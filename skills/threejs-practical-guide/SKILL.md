# Three.js 实战指南

当任务涉及 three.js 场景初始化、黑屏排查、模型不可见、渲染器调优或性能优化时，使用这个技能。

## 工作方式

- 优先做最小修改，用来验证或排除某个假设。
- 把性能建议当作假设，而不是铁律。修改前后都要测量。
- 除非项目明确使用其他比例，否则默认 `1 unit = 1 meter`。
- 尽量让场景围绕原点构建，减少大坐标带来的浮点误差。
- 不要移动根 `Scene`；优先移动相机、控制器或子对象。

## 首先处理：什么都看不见

当场景只渲染出黑色或空白画布时，按这个顺序检查：

1. 先看浏览器控制台报错。
2. 把场景背景改成醒目的测试颜色，确认渲染是否真的在发生。
3. 把相机从原点往后移。
4. 确认物体在相机视锥体内。
5. 确认物体有灯光照亮，或临时用 `MeshBasicMaterial` 绕过光照。
6. 检查物体缩放是否异常，大得离谱或小得离谱。

常用探针：

```js
scene.background = new Color("red");
```

```js
camera.position.z = 10;
```

```js
camera.far = 100000;
camera.updateProjectionMatrix();
```

```js
scene.overrideMaterial = new MeshBasicMaterial({ color: "green" });
```

结果判断：

- 出现红色背景：说明渲染器在工作。
- 只有换成 `MeshBasicMaterial` 才能看到物体：大概率是灯光缺失或灯光配置错误。
- 调大 `camera.far` 后物体才出现：大概率是视锥体设置有问题。
- 只看到一个小点或出现严重裁剪：大概率是缩放比例不一致。

## 默认工程规则

- 复用对象，不要在循环或动画帧里频繁分配新对象。
- 不要每帧都创建 `Vector3`、`Color`、数组或临时对象。
- 优先使用 `BufferGeometry`。
- 在可以共享的前提下复用网格、材质和纹理。
- 模型交付优先使用 glTF，不要优先选择 OBJ、COLLADA 这类老式文本格式。
- 如果资源体积重要，优先考虑 Draco 或 `gltfpack` 压缩 glTF。

## 相机建议

- 让 near/far 裁剪面尽可能贴近实际需求。
- 不要把重要几何体放在 far 裁剪面附近。
- 调试阶段可以把视锥体放大，正式环境要尽量收紧。

## 渲染器建议

- 合适时开启高性能 GPU 偏好。
- 除非确实需要，否则不要启用 `preserveDrawingBuffer`。
- 除非场景真的需要，否则不要开启 alpha、stencil 或多余的 depth 缓冲。
- 静态场景优先按需渲染，而不是每一帧都渲染。

`OrbitControls` 的常见写法：

```js
controls.addEventListener("change", () => renderer.render(scene, camera));
```

只在变化时渲染，通常带来的收益不是更高 FPS，而是更低发热和更省电。

## 灯光与阴影

- 大多数材质都需要有效灯光才能看见。
- 动态直射光越少越好。
- 不要频繁增删灯光；优先用 `visible = false` 或 `intensity = 0`。
- 点光源阴影尤其昂贵，因为需要渲染六个方向。
- 如果阴影不需要持续刷新，只在场景变化时更新。
- 阴影视锥体范围和阴影贴图分辨率都要尽量小。
- 用 `CameraHelper` 检查阴影视锥体。

## 材质

- 对哑光表面，`MeshLambertMaterial` 往往可以作为 `MeshPhongMaterial` 的低成本替代。
- 如果网格使用 morph targets、morph normals 或 skinning，确保材质开启了对应选项。
- 带骨骼或形变的网格不要盲目共享材质；需要时用 `clone()`。
- 自定义 shader 的 uniform 只在值变化时更新。

## 纹理与颜色

- 条件允许时优先使用 2 的幂尺寸纹理。
- 在画质可接受的前提下，纹理越小越好。
- 如果替换新纹理更简单更便宜，就不要原地改尺寸。
- 相同尺寸的 JPG 和 PNG 上传到 GPU 后，显存占用通常差不多。
- 颜色、自发光、环境类纹理通常需要按 sRGB 处理；非颜色数据纹理一般保持线性空间。

版本提醒：

- 较旧的 three.js 项目可能还在用 `outputEncoding` 和 `texture.encoding`。
- 较新的项目则改用 color-space 相关 API。
- 修问题时要跟随项目当前 three.js 版本，不要混用两套写法。

## 透明、抗锯齿与后处理

- 透明物体开销很高，尽量少用。
- 如果只需要裁切效果，优先 `alphaTest`，不要直接上完整透明。
- 内置 MSAA 往往比额外叠 FXAA/SMAA 更划算，但还是要以 profiling 结果为准。
- 每个后处理 pass 都会增加整屏渲染负担，能合并就合并。
- 如果后处理要求手动抗锯齿，记得关掉没在用的内置 AA 路径。

## 性能排查

性能差时，先判断瓶颈在 CPU 还是 GPU：

1. 临时用基础材质覆盖场景材质。
2. 对比修改前后的帧时间。

结果判断：

- 提升明显：大概率是 GPU 瓶颈。
- 提升不明显：大概率是 CPU 瓶颈。

然后重点检查：

- draw calls
- 像素比
- 阴影数量和分辨率
- 透明物体数量
- 动态灯光数量
- 顶点数和动画成本
- 后处理 pass 数量

高收益优化项：

- 在移动端把设备像素比上限控制在 `2` 或 `3` 左右。
- 对静态对象设置 `object.matrixAutoUpdate = false`，变换后手动调用 `updateMatrix()`。
- 远处物体使用 LOD。
- 远处物体或动画降低更新频率。
- 能接受时，用 billboard 替代远处复杂几何体。
- 大量相似网格优先使用 instancing。
- 粒子或顶点动画规模很大时，尽量转到 GPU 上处理。

## 常见视觉问题

- Z-fighting：把其中一个面轻微错开，比如 `0.001`。
- 大世界抖动：让活动区域尽量靠近原点，或引入缩放策略。
- 细密重复结构如百叶窗、栏杆：抗锯齿伪影很常见，可考虑用纹理或 impostor 替代。

## 删除与更新

- 如果对象之后还会回来，优先隐藏，不要销毁。
- 临时移除时优先使用 `object.visible = false`、`material.opacity = 0` 或 `light.intensity = 0`。
- 永久移除的 GPU 资源要正确 dispose。
- 做运行时更新前，先判断是否真的需要新几何体、材质重编译或纹理替换。

## 推荐处理流程

在处理 three.js 问题时，按这个流程组织：

1. 先判断问题是可见性、正确性还是性能。
2. 先做最小诊断动作，尽快缩小原因范围。
3. 用直接、通俗的语言解释最可能的根因。
4. 修复方案要和项目当前的 three.js 版本兼容。
5. 用可验证结果收尾，比如模型出现了、draw calls 降了、帧时间下降了、shader 重编译减少了，或 GPU 压力降低了。
